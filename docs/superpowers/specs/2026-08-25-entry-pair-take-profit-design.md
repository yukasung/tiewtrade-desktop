# Entry Pair Take Profit และตาข่ายระดับ Basket

วันที่: 2026-08-25

ต่อจาก [2026-08-24-basket-take-profit-sweep-design.md](2026-08-24-basket-take-profit-sweep-design.md)

## ปัญหา

หลังเปลี่ยนไปใช้ Basket Take Profit ระดับเดียว (24 ส.ค.) Basket ทั้งใบต้องรอเป้าเดียวกันหมด
ผู้ใช้ต้องการให้ **Entry Pair เป็นหน่วยที่ถูกขาย** — แต่ละ Pair มีราคาเฉลี่ยและเป้าของตัวเอง
ปิดแยกกันได้ โดยยังคงเป้าระดับ Basket ไว้เป็นตาข่ายรองรับ Pair ที่ตลาดทิ้งไว้ข้างหลัง

## การตัดสินใจ

### 1. ลำดับก่อนหลังใน candle เดียว — Pair ก่อน แล้วจึงกวาด

ถ้า candle เดียวแตะทั้งเป้า Pair และเป้า Basket: Pair ที่ถึงเป้าตัวเองขายที่**เป้าตัวเอง** จากนั้น
ส่วนที่เหลือถูกกวาดที่เป้า Basket

เหตุผล: สำหรับ LONG เป้า Pair ที่ถูกกว่าย่อมต่ำกว่าเป้า Basket การขายที่เป้า Basket แทนจะเป็น
การสมมติว่า limit order ที่ราคาต่ำกว่าไม่ได้ Fill ก่อน ซึ่งเป็นการนับกำไรที่ตลาดยังไม่ได้ให้ —
กติกาเดียวกับที่ `PRODUCT.md:162` ใช้กันการสมมติลำดับราคา intrabar

### 2. Take Profit ทุกแบบ book เป็น exit รายไม้

ทั้ง Pair exit และการกวาดถูก book เป็น Fill รายไม้ แล้ว Basket ปิดเมื่อไม้สุดท้ายหมด
(`settled_result`) ถ้าทำการกวาดเป็น Fill ก้อนเดียวจะชนกับ invariant ใน
`persistent_paper_spot_session.py` ที่ห้าม entry exit มาคู่กับ whole-basket exit ใน snapshot
เดียวกัน — ซึ่งเกิดขึ้นแน่นอนเมื่อ candle เดียวทำทั้งสองอย่าง Stop loss ยังเป็น Fill ก้อนเดียว
ตามเดิม เพราะมันไม่มีทางเกิดพร้อม take profit

### 3. `TakeProfitExit` พก raคาที่ตัวเองออกมาด้วย

`Basket.take_profit_exits(high, low)` คืน `(entry, price)` ไม่ใช่แค่รายการ Entry เพราะไม้ที่ออก
ใน candle เดียวกันอาจออกคนละราคา — บางไม้ที่เป้า Pair บางไม้ที่เป้า Basket ถ้าคืนแค่ Entry
executor จะต้องเดาเองว่าไม้ไหนออกด้วยกฎข้อไหน ซึ่งเป็นการอ่านกฎซ้ำที่ไหลออกจากกันได้

### 4. ค่าของ Pair เดินทางผ่าน `BasketPair` ไม่ใช่คำนวณซ้ำที่ UI

`Basket.open_pair_views()` แถลงราคาเฉลี่ยและเป้าของทุก Pair ที่ยังเปิด ค่านี้เดินผ่าน
session snapshot → `BasketSnapshot.pairs` → `BasketSnapshot.pair_for(entry_number)`
ให้แถวใน UI อ่านของ Pair ตัวเอง

ทางเลือกที่ไม่เลือก: ให้ `paper_basket_projection` คำนวณเป้า Pair เอง — จะเป็นการทำสำเนา
สูตรและการปัด tick ไว้นอกโมดูล `trading` ซึ่งผิด ownership ใน `ARCHITECTURE.md` และเป็น
กฎที่พูดสองที่จนไหลออกจากกันได้

## ⚠️ ขอบเขตของตาข่าย — ต้องบอก ไม่ใช่ปล่อยให้เข้าใจผิด

ราคาเฉลี่ยของ Basket อยู่ระหว่างราคาเฉลี่ยของ Pair ที่ถัวลงต่ำสุดกับสูงสุดเสมอ ดังนั้น:

- **ราคาค่อย ๆ ขึ้น** → แต่ละ Pair ถึงเป้าตัวเองแล้วออกไปก่อน จนเหลือ Pair เดียว ซึ่งราคาเฉลี่ย
  ของมัน **คือ** ราคาเฉลี่ยของ Basket ทำให้เป้าทั้งสองเท่ากันพอดี **ตาข่ายไม่มีผล**
- **ราคาพุ่งแรงใน candle เดียว** ข้ามเป้า Basket ไปเลย → ตาข่ายทำงาน กวาด Pair ที่ติดดอย
  ออกที่ราคาต่ำกว่าเป้าตัวเอง

แปลว่าตาข่ายนี้กัน **การฟื้นตัวแบบเร็ว** ไม่ได้กัน "ติดดอยยาว ๆ" ซึ่งเป็นเคสที่ทำให้เกิดงาน
เมื่อ 24 ส.ค. Pair ที่ติดดอยยาวยังต้องอาศัยการปิดเองของผู้ใช้ ข้อนี้ถูกเขียนไว้ใน `PRODUCT.md`
§5 และ `CONTEXT.md` ด้วย เพื่อไม่ให้อ่านว่าตาข่ายรับประกันการปิดรอบ

ตาข่ายไม่ได้รับประกันกำไรด้วย — acceptance test
`test_the_basket_target_sweeps_out_the_pair_the_market_left_behind` จงใจจบด้วย realized PnL
ติดลบ เพื่อบันทึกว่าสิ่งที่ตาข่ายรับประกันคือ *รอบจบ* ไม่ใช่ *รอบกำไร*

## ผลกระทบที่ต้องบอก

Basket ที่เปิดค้างข้ามการอัปเกรดจะได้เป้าชุดใหม่ทันทีที่ Runtime หยิบกลับมา — เป้า Pair ไม่เคย
ถูกเก็บลงฐานข้อมูล (คำนวณใหม่จาก `trade_fills.entry_atr` ทุกครั้ง) จึงไม่มีอะไรให้กู้คืน

ค่าคาดหวังของ deterministic replay (`23.679`) ไม่เปลี่ยน เพราะ Basket ใน
`tests/fixtures/btcusdt_5m_tracer.csv` มี Entry เดียว ซึ่งเป็น Pair เดียวและเป็น Basket ทั้งใบ
เป้าทั้งสามระดับจึงเป็นราคาเดียวกัน
